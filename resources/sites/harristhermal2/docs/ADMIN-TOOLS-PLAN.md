## 2. The agreed handoff model (Chris's email to Steven, 2026-09-03)

1. Steven keeps working in Eleventy while the changes are structural: new pages,
   moving content around. Staging can be refreshed from any commit meanwhile.
2. When he is down to swapping graphics and fine-tuning text, he re-posts the
   project. We import it **once**. That import becomes the live site.
3. From then on SiteHub is the source of truth and his Eleventy project is the
   archived original. **No re-imports after cutover.** Structural changes after
   launch are edits to the Blade in our repo; routine changes go through admin tools.
4. He logs in to our admin to finish graphics and text.

This is the spec's flatten-first model: capture once, pages become code, editable
surfaces built against real demand. The one-way rule is what keeps the two copies
from drifting; it must stay explicit with the client.

## 3. Admin tools Chris wants

- Menu builder
- Common header and common footer
- Inline text editor
- Inline photo editor: swap image and set SEO (alt / title / og)

Plus one that is not on the list but that Harris will hit first: **posts**. They
publish Industry Insights monthly. The site has 23 posts, 8 category archives and
107 tag archives, all generated by Eleventy. Without a posts feature the first new
article after cutover means hand-building archive pages.

## 4. Decisions to settle before building (the worries)

1. **Never write edits back into Blade files.** The web process writing into
   `resources/` is a code-injection surface, trips the July integrity monitor, and
   makes the server checkout diverge from git so the next pull overwrites client
   edits. Edits are database overrides keyed to a region, merged at render. Pages
   stay code. (The spec's legacy do-not-reproduce list includes on-page inline
   editing for this reason.)
2. **Flattening destroys his single-source chrome; the importer must put it back.**
   Header, footer and nav are currently baked into all 201 pages. Change the
   importer to split each page into a content section and emit pages that
   `@extends` one shared layout (as FRAN does). Header and footer become one file
   each, footer facts read from site settings, the menu builder edits one source.
   **Do this before the final import.**
3. **Menus as data reverses a spec non-goal** (navigation-is-code, spec section 15).
   Reverse it consciously: tenant table or settings jsonb, a two-level Filament
   repeater, a nav component that emits his exact markup.
4. **Stable keys, and the one-way rule for real.** Every override needs a key that
   survives page regeneration. A re-import or a renumbering after cutover wipes the
   client's edits.
5. **"Inline" means in the admin with a preview link, not contenteditable on the
   live page.** Same UX for the user, none of the exposure (authenticated write
   endpoint into markup, sanitisation, cache handling).
6. **An image is not one `src`.** Pages carry WordPress-era `srcset` derivatives,
   CSS background heroes, and absolute `og:image` / JSON-LD image URLs. An image-slot
   component emitting `srcset` from medialibrary conversions covers the HTML ones;
   CSS backgrounds and head meta need their own slots. "Set SEO" splits into alt
   text on the slot and a per-page meta editor (title, description, og:image).
7. **Baked structured data drifts from edited text.** His FAQ accordions and their
   FAQPage JSON-LD render from one front-matter array; after flattening they are two
   copies. Either FAQs become data (small feature) or they are excluded from the
   text editor.
8. **Every admin save flushes the response cache.** Today the platform clears
   globally (`ResponseCache::clear()`); per-site tags per the spec would be better
   but global is acceptable at this scale.

## 5. The fork to decide first

**(a) Edit baked HTML with keyed overrides**, or
**(b) bring his data into features and flatten only the markup.**

His nav (`config/nav.json`), site facts (`config/site.json`), FAQs (front-matter
arrays) and posts (`src/posts/`, `_data/posts.json`) are already data. Importing
those into features is more work at import and far less fragile afterwards.

Recommendation: **(b) for nav, site facts, posts and FAQs; (a) keyed overrides for
everything else.**
